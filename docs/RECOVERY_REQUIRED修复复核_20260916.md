## 本次确认并修复

1. **同一工作区存在两个服务实例。** 现场确认 8765、8766 同时运行。旧启动器自动换端口，使两个进程可以读写相同世界。现在使用操作系统持有的工作区锁，且不再自动更换端口；进程退出自动释放锁。再次启动时会先验证 8765 确实是本项目服务，然后复用已有页面并正常退出，不再打印锁异常堆栈。
2. **运行中审计误读中间状态。** Pixel 文件、SQLite 和世界回合不是同一次写入。现在运行中明确显示 RUNNING / 审计延后；空闲时在控制器锁内进行完整审计，不将正常执行中的预留和文件同步窗口展示为恢复故障。
3. **成功响应没有落库，结算与响应状态分离。** 现在成功/格式错误响应记录、结算、消息状态在同一个 SQLite 事务内提交。失败则整体回滚；运行报告改读实际数据库及正确预算字段。
4. **后续调用失败导致已完成消息的回合信息领先世界。** 若本轮已有成功结算，异常收尾保留已发生的回合与消息队列，不冒充回滚；第一笔调用即被明确拒绝时，不空推回合。
5. **异常清理不完整。** 启动数据库失败、线程启动失败、末轮停止和快照失败均明确结束/报错；快照失败不再让控制器永久保持运行中。Loop 元数据改为原子替换写入。
6. **调用异常处理可能重复请求或捏造账目。** 移除 TypeError 后再次调用和 SDK 自动重试；使用异常类型区分明确拒绝与结果未知；缺少用量不再按预留金额虚构实际扣费。有效 usage 的 JSON 格式错误仍准确结算并结束为 ERROR。
7. **延期消息可能重复恢复。** 延期时同步清除 in_progress，避免同一消息同时存在于两个队列状态。
8. **模型偶发漏写 JSON 结束括号。** 仅允许补齐由括号栈唯一确定的 `]` / `}`，补齐后仍执行完整 JSON 与响应 Schema 校验；不补逗号、不续写字符串、不猜测内容。本次已结算的失败响应经此规则验证后复用，不重复调用 API，原失败 Run 仍保留为真实历史。
9. **Windows 前端读与演化写发生共享冲突。** 对同一 JSON 文件的进程内读写使用同一把锁；原子替换仅在 Windows 短暂 `PermissionError` 时有限重试，其他异常立即失败。队列文件统一使用相同原子写入实现，并加入高频并发读写回归。
10. **OWNER_ACTION_REQUIRED 无前端审批入口。** 前端现在持续读取并展示所有待处理请求，要求 Owner 填写明确答复后批准或拒绝；通用 V9 请求不再错误要求 `profile_file`。存在待处理请求时后端和演化按钮都会阻止新 Run，处理完后由 Owner 手动继续。

## 不能承诺的边界

## 1. 一句话目标和成功标准

**卡住后先找适用的其他办法，能继续的先继续；走不通时保留成果并让老板接手，不能反复打转，也不能把未完成写成完成。**

实施后必须跑通三条完整路径：

1. 普通步骤原方法失败 → 换一种有区别的方法 → 取得真实结果 → 继续后续步骤。
2. 前一步仍缺资料 → 带着已有成果、缺口和失败次数进入允许继续的后一步 → 后一步补查或完成不受影响的工作 → 明确交付完整或部分成果。
3. 自动办法用尽 → 保存进度并提示老板 → 老板补资料、返工、调整普通要求或明确跳过 → 新执行确实使用这次决定，历史记录和次数仍在。

三条路径均须保持：独立工作继续；公司 OFF 不被自动改为 ON；未知费用和未知外部结果按现有核验规则处理；同一问题及整个自动执行范围都有上限。

## 3. 范围与最小实现原则

首期覆盖**公司 Worker 路径上的已批准 TaskPlan**：普通内部调研、资料整理、草稿及交付物加工，以及 BOSS 中对应的进度查看和人工续办。

- 保留现有 Goal / TaskPlan / Task / Attempt / Worker / Ledger 分工；在现有服务内增加推进规则，最多增加一个薄的 `company_progress_service.ts` 管缺口、额度和恢复命令，不建立第二套调度器。
- 不引入工作流框架、消息队列或新数据库服务；不重写旧 World/Core、商城、订单、收款或发布系统。
- 旧计划缺少新字段时继续按原严格要求运行。新的宽松要求必须进入可审阅、可批准的计划；已有普通计划可由老板显式调整，不静默放宽。
- 容错只选择当前已启用、已获准且适合问题的工具和来源。没有替代来源时允许明确转人工，不为每种失败执行一遍所有“兜底”。
- 外发、支出、凭据、软件发布等仍走各自现有授权。金额、事实真实性、文件 hash、付款核验和未知副作用不能按百分比放行。
- 本计划要求升级保留经营数据；不使用 V34 清零重置解决兼容问题。发布操作不在本轮授权范围内。

## 4. 每个环节怎样继续推进

### 4.1 普通要求与必要限制分开

在 `CompanyTaskNode` 增加可选 `progressPolicy`，首期只包含：稳定编号的普通验收项、通过比例，以及允许接收不完整输入的前置节点键。原 `dependsOn`、`filename`、`trigger` 等结构继续使用。

1. 原 `dependsOn` 默认是必须满足的依赖；`progressPolicy.allowIncompleteFrom` 只能是它的子集。老板批准的普通内部工作可以明确允许某些输入缺失，由后续步骤补查。
2. 普通要求先有清单，再谈比例。例如 5 项完成 4 项是 80%；没有清单依据的工作显示“完成 / 部分完成 / 待补充”，不显示虚假精确百分比。
3. 模型可以给出某一项完成的依据或建议，程序核对可自动核对的部分。模型自报“有八成把握”不算完成 80%。
4. 普通阈值可选 70%、80%、100%；本 Plan 建议新获批的普通收集环节从 80% 起步。旧计划保持 100%；实际启用值随批准计划保存。
5. 必要授权与事实校验由原业务服务判断，不能由模型把它们标成“普通项”后跳过。草稿可以继续，未经核验的收入和外部动作不能因此成立。
6. 普通要求改动保存前后版本、操作者和理由，不能删除未完成项来提高比例，也不能清空尝试次数。改变实际授权、依赖范围或定时安排时走新版本审批。

### 4.2 保存真实结果，不改写底层执行事实

节点 / occurrence 在原状态之外增加三种必要表达，最终名称在协议中统一：

| 状态 | 含义 | 对后续的影响 |
| --- | --- | --- |
| `PARTIAL` | 已有可核验的部分成果，达到本轮获批普通通过要求 | 只有允许不完整输入的后续节点可以接收；缺口继续保留 |
| `DEFERRED` | 本环节自动办法暂已用尽，记录缺口后先做获准的其他工作 | 允许补查的后续可以继续；必要依赖分支等待；不自动反复唤醒本节点 |
| `SKIPPED` | 老板明确跳过的普通环节 | 保留决定和影响，不能算作成功产物 |

原 `COMPLETED` 继续表示该环节按要求完成；`occurrences` 保持既有成功次数含义，不能靠跳过加一来骗过依赖判断。周期统计另区分执行、完成、部分及跳过。

Attempt 继续使用现有状态。**Worker 正常返回、Task REPLIED，不等于环节完整通过**；由控制层依据真实回执、产物和要求判定节点结果。失败 Attempt 中已经落盘并核验的有效产物也应保留和评估，不能因最后一步失败而丢弃。

缺少必要事实、未知执行或待授权操作时，该动作继续等待。可继续的其他部分由原调度器调度；等待期间不持续调用模型。

### 4.3 后续步骤收到什么

每次派工输入同时包含：本轮要求、已核验的产物引用和 hash、未完成项 ID、已试方法及结果、剩余次数、允许继续的范围、受影响的动作。

- 前置结果为空时仍可创建获准的普通补查步骤，明确写“输入缺失”；不能伪造一个前置文件。
- `READ_TASK_DEPENDENCY` 只允许读取本步骤获准接收的实际产物；扩展它对合法部分产物的读取，仍核对 Goal、版本、依赖关系和 hash。
- 补查由后续当前步骤执行，不把调度图连回上一节点。若需再次处理原节点，由显式续办创建有次数限制的新执行，保持原 DAG 无环。
- 一次性工作不再有可自动执行部分时进入人工处理或交付部分结果；“可执行节点为空”不能长期显示正在运行。

## 5. 多种解卡方式及使用条件

| 卡点 | 首先允许做什么 | 仍走不通时 |
| --- | --- | --- |
| 一个公开资料地址不可用 | 在额度内重取明确可重读的请求，或改读另一个适用且允许访问的来源 | 保留缺口，继续分析已取得资料或转后续补查 |
| 资料不足 | 调整查询范围、查允许的其他来源、读取获准依赖或合适 Skill | 不编造数据，按获批规则部分交接或请求补材料 |
| 一次工具返回失败 | 将真实错误反馈给 Worker，让下一次请求解释改变什么；只读与有副作用动作分开判断 | 不重放未知写操作，选其他合法工作或转人工 |
| 模型格式错误 | 在当前额度内做一次明确的格式纠正，保留已付费响应 | 再失败时保存已有成果和原因；不无穷修 JSON |
| 模型请求确定未发出 | 沿用现有最多 1 次补发；两次实际发起均记入公共尝试额度 | 暂缓本项，其他已获准工作继续或等待人工 |
| 模型请求已发出但结果未知 | 复用已存回执或走现有恢复核验，原预留保留 | 不把“换方法”变成偷偷重发这笔未知请求 |
| 已有模型结果但费用未核实 | 沿用现有执行和记账分离：获准、预算可满足的其他工作可继续 | 未决账单独立保留，不填写假零费用 |
| 没产出指定文件或没有新增内容 | 提供明确缺项和已试办法，最多选择剩余的有区别方法 | 暂缓、部分交接或人工续办；不只等 5 秒重跑原指令 |
| 等待招聘 / 授权 / 预算 | 处理其他可执行工作；条件满足后按原规则恢复 | 不重复申请同一事项，不把拒绝当批准 |
| 人工要求返工 | 下一次执行携带确切返工要求及已有成果 | 执行后重新提交绑定新版本的结果，不能只修改备注 |

一次失败不要求执行表中所有分支。选用理由要能够说明“为什么适用、与上次有何区别”；没有适用办法就明确结束自动尝试。

## 6. 怎样防止跨环节无限循环

### 6.1 同一问题共用一份缺口记录

每个缺口记录：稳定 ID、所属目标、原始事实对象和时间范围、关联验收项、影响节点、尝试方法、实际调用 ID、结果、累计次数、当前处理方式和版本。

- 已知验收项以“验收项 ID + 对象 + 原始事实时间范围”关联同一缺口；后续节点必须引用原 ID。换词、换来源、换 Worker、返工、修订计划不重新编号。
- 模型临时发现的问题由控制层分配 ID，并受整轮总额度限制；不声称程序能完全识别任意语义改写后的同一问题。
- 同一缺口首期最多 **3 次实际求解尝试，包含第一次**。已返回结果的恢复读取不算一次新尝试；真正重新请求才计数。原方法的网络补发不能在外层再领一份完整额度。
- 连续 **2 次无新增有效信息**，该方法提前停止；仍可在剩余额度内选不同办法。相同资料、换措辞和提高自评分不算新增信息。
- 同一历史事实不能因到了明天而重获 3 次机会；确实在核查新日期、新对象的事实，才是新的问题。

### 6.2 整个自动执行范围另有限制

下列为本 Plan 建议首期值，实施时写为受控配置，并在批准计划中展示；不是从 IRO_agent 直接复制的项目现值：

| 限制 | 首期建议 | 说明 |
| --- | --- | --- |
| 单 Worker 步数 | 保持现有最多 20 步 | 不因修格式或换法绕开 |
| 同一缺口尝试 | 3 次 | 跨节点、Attempt、返工及重启累计 |
| 一轮自动工作模型发起次数 | 60 次 | 包含规划、纠正、求解和确定未发出后的补发 |
| 一轮自动工作工具实际执行次数 | 120 次 | 包含读取、写产物及补查，不按模型一次批量请求算一次 |
| 一轮自动工作窗口 | 15 分钟 | 持久保存开始和截止时间，每次调用还须受各自实际超时约束 |

一次性目标共用一个预算范围。长期经营沿用已批准的定时触发建立有限工作批次：到下一次合法触发可以创建新批次；同次触发中的失败重试、跨节点补查和人工返工仍属于原批次。后续补查继承来源批次 ID，不能借创建新节点、修改 `scheduled_at` 或轮询来刷新额度。

不额外发明长期任务的“每天清零”语义。已有触发无法唯一判定批次归属时，先在 P1 的契约中明确该计划的归属规则并加用例，不能由模型自己决定。稳定缺口的累计限制跨批次仍然有效。

- 计数由控制层在许可发出或工具执行前原子保存。模型发起按 `(operationId, transportAttempt)` 区分真实补发和同一次许可的恢复重取；重复回执、读取已存响应不重复扣减。
- 预启动金额预留与实际执行计数分开；未发起的准备操作不冒充已花费用，发起后中断也不悄悄退还尝试次数。
- 普通继续、重开、版本升级不刷新额度。老板可明确追加有限次数或时间，完整请求只生效一次；AI 无权自动追加。
- 人工等待不发起新调用。老板明确继续可授权新的有限时间窗口，历史尝试及费用继续累计。
- 金额预算始终独立生效；有剩余次数不等于有权花费。不得恢复已经删除的个人预算或另一套费用账本。

### 6.3 超时必须落实到实际调用

复用 ModelProvider 的 AbortSignal 和工具现有取消能力，调用超时取“自身上限、当前窗口剩余时间”的较小值。不要只在返回后检查时间。

控制层 RPC 等待超时不证明底层操作已停止。只读操作确认退出后可按额度补查；写动作结果不明进入既有 UNKNOWN 核验。Windows Worker 接管继续要求 PID/birth/退出证明，不能仅因租约到期再启动一份。

只补本期调用链中查明的取消缺口，不改造全部工具执行架构。

## 7. 最少保存哪些新增信息

继续使用公司控制 SQLite、原 TaskPlan 表、产物证据表、Worker journal 和审计事件。

1. 已批准计划正文保存新增普通要求和交接规则，随 `planRevision` / 要求版本绑定批准。
2. 节点 / occurrence 保存本轮结果和覆盖情况，历史结果不可被后续返工覆盖；原产物仍存原证据位置。
3. 新增两张小表即可作为首期落点：`company_progress_scopes` 保存批次归属、限额、消耗、截止时间及 revision；`company_progress_gaps` 保存稳定缺口及有界尝试记录。用原控制事件记录人工修改和追加，不另造事件数据库。
4. 进度表不拥有 Task/Attempt 执行状态、不写金额账本。调度只能调用原计划与执行服务改变其各自状态。
5. 对新字段、表和 Worker 输入做显式格式版本管理。已存在的冻结 spec / command / journal 不就地补写新字段，不改变它们的 hash；旧 Worker 可完成原尝试，后续新 Attempt 再使用新契约。
6. 迁移只做可验证的增量转换；保存旧 Goal、任务、产物、账单、未知结果和 OFF 意图。不认识的格式保留原数据并给出准确处理提示，不能清库或静默当作全新实例。
7. 普通要求调整不自动增加 `specificationRevision` 导致整套当前计划消失；使用独立要求版本并更新批准绑定。确实改变目标范围时沿用现有目标修订流程，保留缺口和尝试的显式继承关系。
8. 数据库不可写时停止新增执行并返回能展示的当前摘要；不能继续跑一段无法可靠保存的任务，也不到别的目录临时建立另一份状态。

**最终结果表达：**完整验收继续使用 `COMPLETED`；新增 `PARTIALLY_COMPLETED` 表示老板接受现有部分成果并结束本轮目标，必须显示未解决项。所有目标终态判断、重开、归档、统计、提案、产品联动和双语文案同步适配；不能只新增一个枚举而漏掉原控制分支。长期目标某轮部分完成记在 occurrence，目标是否继续仍按原经营意图和触发规则处理。

结案继续复用 `close_task` 提案，新增明确的 `completionKind: full | partial`，快照绑定实际证据（允许为空）、要求版本、未解决项及返工轮次。完整结案沿用原证据条件；部分结案要求老板明确接受当前成果及缺口，落为 `PARTIALLY_COMPLETED`，不增加“已核验完整交付”或收入统计。

没有任何真实产物时也能交付程序生成的进度与缺口摘要；摘要不是产物或付款证据。此时允许停止、等待或由老板接受无产物的部分结果，不能伪造证据以通过现有完整结案检查。

## 8. 老板操作必须真的影响下一步

### 8.1 复用入口，补少量命令

先修复现有 `GET/POST /owner/tasks/:id/actions` 的字段契约：入口验证完整请求白名单，再拆出 `action` 将其余字段交给对应服务，继续拒绝任意多余字段；保留 `STOP_TASK`、`RETRY_TASK` 的原含义。新需求以最少扩展承接：

- 任务级增加 `REWORK_TASK`，明确接收返工要求；不继续借用 `reason` 兼任执行指令。
- 节点级增加 `GET/POST /owner/goals/:id/nodes/:key/actions`，承接补材料并继续、调整普通要求、跳过普通环节、追加有限额度。节点尚未生成 Task 时也有入口；内部复用同一薄服务和原计划事务。
- 停止 Goal、费用核验、未知执行放弃继续走原端点，不混进新节点命令。对于已核验但历史 reason 仍为 UNKNOWN 的 Attempt，依据实际 review、账单、工具回执及退出证明计算允许的后续动作；不只看旧错误字符串，也不修改旧终态。

新增或修改动作绑定 Goal、节点、目标 / 计划 / 要求版本和完整请求内容，沿用 Owner 鉴权及持久幂等键。服务端重新计算可用动作；GET 和 POST 的准入条件必须一致。可记录续办决定与“能立即运行”分开，公司 OFF、暂停或维护时不启动模型或工具。

人工命令事务内只保存决定和可恢复的续办意图；模型和工具调用在事务外由原调度路径执行。提交与进程中断之间依靠持久意图续办，不能把异步网络调用塞进 SQLite 事务或以接口超时为由重复创建任务。

### 8.2 返工的具体闭环

1. **失败任务返工：**保留旧 Attempt 和费用；新 Attempt 指令由原批准要求、返工说明、已有成果、缺口和剩余额度组成。只修改新执行输入，不改旧 spec。
2. **计划返工：**旧提案拒绝后，执行一次有上限的计划修订，产出可审阅的新计划及新 hash；新计划重新批准前不执行，不能自行扩大权限。
3. **交付返工：**确定要修订的普通节点，建立可调度的返工 occurrence / 派工；全部节点已完成时也必须有实际返工落点。范围不明确时先向老板说明需要指定哪项，不能把 Goal 改成 RUNNING 后空转。
4. **再次交付：**结案快照同时绑定证据、要求版本和返工轮次；旧拒绝提案不能堵住新一轮，也不能因反复轮询生成新提案。
5. 老板修改普通要求、补材料或跳过时保留历史累计。人工材料标明来源，不能冒充系统独立核实的事实。

### 8.3 BOSS 的展示

沿用首页最多三个事项及“其他待处理”入口，自动换法的普通日志进入公司视察，不占老板决策席位。

每个受阻事项展示：已完成内容、缺什么、试了什么、还剩几次、建议下一步及影响。主要交互继续采用“通过 / 拒绝 / 返工”：通过执行明确建议，拒绝停止这项建议并按剩余授权选择其他办法，返工展开补充输入；跳过、调整要求、追加额度放在该事项的展开区，不新增一套主页导航。

拒绝重试不自动等于跳过依赖或完成任务；STOP_TASK 也不能被解释成“下游全部可以继续”。确需跳过必须有明确动作和记录。

请求未确认时保存完整字段和原幂等键，刷新、折叠、语言切换不丢失待确认操作；只重试原请求。旧 revision 显示当前变化并保留输入。处理后只有真正解决的子项消失，未核验费用或剩余缺口继续可见。

所有新增及变更的标题、状态、按钮、说明、校验错误、服务端可配置文案同时提供中文和英文。同步检查 `zh-CN.ts`、`en.ts`、`boss.ts` 的实际导入关系，不能只改一个未生效词条。

## 10. 验收场景

| 场景 | 必须观察到的效果 |
| --- | --- |
| BOSS 按原请求字段发起继续、停止 | 经过实际 API 路由成功，不被多余 `action` 字段拒绝；额外非法字段仍拒绝 |
| 任务卡片填写返工说明 | 后续真实模型请求包含该说明；旧 Attempt、费用和产物不改写 |
| 计划返工、全节点已完成后的交付返工 | 前者生成新待批计划；后者产生实际返工任务及新验收提案，没有永久 RUNNING 空壳 |
| 同目标 A 失败、B 独立、C 必须依赖 A | B 继续；C 等待必要输入；其他目标正常；公司 ON 保留 |
| A 缺资料、C 获准接收不完整输入 | C 收到缺口和次数，能补查或完成其他内容；前置文件可为空，不伪造文件 |
| 同一缺口在 A/B/C 节点、不同 Worker 或 Attempt 中求解 | 合计达到 3 次后不再自动查；改词、返工、重开和重启不刷新次数 |
| Worker 格式纠正、确定未发出后的补发、工具批量调用 | 逐次记入对应上限；底层和外层不各自获得完整额度；已存结果复用不重复扣 |
| 模型不断创造新缺口、新步骤、重新规划 | 整轮次数或时限生效，有限时间内交出已有结果和未解决项 |
| 5 个普通检查项完成 4 个、获批阈值 80% | 标为部分完成并允许合适后续继续；缺失第 5 项仍展示 |
| 关键授权、hash 或付款核验缺失 | 相关动作继续拒绝，不能通过调低普通阈值执行或记收入 |
| Worker 最后失败但已有合法产物 | 产物和来源保留；节点依据实际内容评估，旧失败不冒充成功 |
| 模型未知结果 / 工具未知写结果 | 不自动重放；核验入口仍可用，已授权的独立工作继续 |
| 已有响应、仅账单待核 | 已知结果可按原规则使用；费用预留保留，不当作零费用，不重复收费请求 |
| 核验后旧 Attempt 的 reason 仍为 UNKNOWN | 根据核验事实给出实际可用的后续动作；旧终态不变；未核验项仍阻止相关重试 |
| 取消、超时或进程断开 | 新调用停止；真实未决操作按 UNKNOWN 留存；未确认退出前不产生第二份 Worker |
| 同一动作双击、超时后刷新、重发旧键 | 原操作只生效一次；追加额度不加两次；完整字段变更被识别 |
| 调整普通要求 / 新版计划替换旧版 | 旧要求与决定可查；不重置缺口和次数；过期批准不能执行新范围 |
| 本轮原定周期结束、下一次合法触发 | 新事实的合法下一轮可执行；旧历史事实缺口不清零；失败重试不伪造新周期 |
| 批准部分交付、完整交付、尚无产物 | 状态和报告分别准确；部分交付不是完整验收；无产物可保存缺口摘要且不伪造证据 |
| 没有新人工操作、没有可执行节点 | 不持续模型调用、不空转重派；等待原因和操作入口可见 |
| 公司 OFF、目标暂停、维护中处理事项 | 决定可按合法范围保存；不启动新执行，不改变原暂停意图 |
| 旧计划、旧 journal、增量升级和兼容回退 | 历史及经营新数据保留；不支持新格式的旧版本明确拒绝切换，并能返回原可用版本处理 |
| 首页超过 3 项、中英文、390×844 | 所有未决事项仍可达；状态、输入、错误及待确认请求两种语言行为一致 |
| 数据库写入失败 | 停止新增动作并明确显示保存失败；已有账单、进度和输出不被虚报为已保存 |

测试优先扩展现有 `company_scheduler`、`company_worker`、`company_worker_adapter`、`company_recovery`、`v35_failure_scope`、`v35_attention_actions`、`boss` 和 `boss_attention`；新增测试仅覆盖缺口交接、共享额度和实际路由等确实没有的行为。

# BOSS「你需要关注的事」交互事件更改说明

日期：2026-10-17（Asia/Shanghai）  
状态：待实施的更改说明。本次只保存文档，未修改运行中的页面、业务数据或发布版本。

## 1. 更改目标

将「你需要关注的事 / What needs your attention」改为老板直接处理事项的交互事件区。

- 所有待老板处理的事件进入同一逻辑队列，首页最多显示 3 张卡片。
- 每张卡片提供与该事件对应的确认、拒绝、选择或输入功能，老板在卡片内完成处理。
- 系统记录决定，按老板选择推进、修改或停止关联流程。只有得到服务端确认才算处理成功。
- 事件重要度随事实更新，每 5 分钟重排一次，展示最重要的 3 件事。
- 暂未展示的事件继续保留，不能因排在第四名以后而丢失。

本次更改针对事件交互和排序。保留现有目标、审批、预算、执行和费用账本的权威状态及权限边界。

## 3. 什么是一个事件

事件必须对应真实、尚待老板处理的业务事项，包括：

1. 目标或执行阻塞，需要核验、调整、继续或停止。
2. 计划、招聘、交付结案等审批，需要确认或拒绝。
3. 预算、收款或模型配置缺失，需要配置或提交明确处理信息。
4. 费用或外部动作结果未明，需要依据回执核验。

已完成且无需老板决定的普通进展，放在「视察公司 / Inspect Company」的记录中，不占这 3 个处理席位。需要老板验收结案的交付仍属于待处理事件。

同一次事故的 Goal、Task、Attempt、调用告警合为一个事件，卡片列出相关状态和操作。相同 Goal 下互不相同的审批不能因去重而丢失；合并展示时须保留每项独立决定。

事件至少包含：稳定事件 ID、类型、标题、原因、关联业务 ID、当前状态与版本、首次需要老板处理的时间、实际截止时间（若有）、允许动作、字段校验、评分及评分依据。业务版本变化不能靠换事件 ID 清空草稿或等待时间。

## 4. 重要度评分：满分 100

采用固定规则，不调用模型打分，也不根据模型自称「紧急」提高分数。

**总分 = 阻塞分 B + 风险分 R + 时效分 U + 影响范围分 I + 等待分 W。**

| 因素 | 权重 | 取值规则（每个因素取符合事实的最高一档，不叠加） |
|---|---:|---|
| 阻塞程度 B | 35% | 35：已授权经营整体无法继续；25：已付款订单交付或一个目标的当前执行链实际阻塞；15：等待审批或补充配置，尚未授权或启动下一步；0：没有实际阻塞 |
| 风险 R | 25% | 25：已确认的安全事故或错误的不可逆外部动作需要处置；15：已发出的外部写动作结果未知，或已付款订单存在已记录的交付违约风险；8：模型用量或费用未明、预留仍占用；0：普通计划、招聘、配置或结案决定，没有上述风险事实 |
| 时效 U | 20% | 20：已超过实际截止时间；16：距截止不超过 1 小时；10：不超过 24 小时；4：不超过 72 小时；0：超过 72 小时或没有真实截止时间 |
| 影响范围 I | 15% | 15：影响公司全部已授权经营；10：影响至少 3 个不同目标或已付款订单；6：影响 2 个；3：影响 1 个；0：仅预备配置，无实际关联目标或已付款订单 |
| 等待时间 W | 5% | 从首次需要老板处理起，每满 6 小时加 1 分，最多 5 分；普通轮询、错误重试、展开详情不重置时间 |

补充规则：

- B 判断流程卡在什么位置，I 判断影响多少业务对象，不能把多个日志或重复告警算成多个影响对象。
- 截止时间必须来自老板确认的任务要求、有效订单约定或明确系统时限；没有截止时间不生成一个假期限。
- 原任务的模型费用未知，只阻塞该任务时，不能按「全公司阻塞」或「外部写动作未知」打分。
- 收款地址尚未配置、但没有销售任务或订单时，不能按已付款订单风险打分。
- 老板主动设置 OFF 是经营意图，不因暂停本身生成故障事件。
- 费用预留额不能被当成已发生损失。CNY 费用与 USDT 收入不混算成风险金额。
- 当前 `createdAt = 0` 或空值的配置事件不能被解释为从 1970 年等待至今。缺少真实首次时间时，等待因素不参与，显示「时间未知 / Time unknown」。
- 首次时间优先从既有业务记录还原；没有记录就保持未知，不为排序增加一套持久事件数据库。
- 所有待处理事件都参与评分，包括当前未显示的事件；不设置「超过一天就自动消失」。

### 评分示例

| 事件与事实 | B | R | U | I | W | 总分 |
|---|---:|---:|---:|---:|---:|---:|
| 已付款订单交付受阻，已逾期，影响 1 单，等了 18 小时 | 25 | 15 | 20 | 3 | 3 | 66 |
| 已授权经营因预算不足整体无法继续，没有截止时间，刚发生 | 35 | 0 | 0 | 15 | 0 | 50 |
| 单目标模型结果和费用未明，影响 1 个目标，无截止时间，等了 12 小时 | 25 | 8 | 0 | 3 | 2 | 38 |
| 一项新计划待批准，影响 1 个目标，无截止时间，刚提出 | 15 | 0 | 0 | 3 | 0 | 18 |
| 尚无销售任务时预先配置收款地址，刚提出 | 15 | 0 | 0 | 0 | 0 | 15 |

这些是规则演示，不是当前生产订单或实际损失声明。权重固定，事件分值随着阻塞解除、期限临近、影响变化和等待增长而变化。

## 5. 刷新、排序与三个席位

1. 首次进入页面，按最新事实立即计算并显示前三名。
2. 沿用现有每 5 秒读取事实的节奏，更新事件状态、可用动作和评分；「实时」在本轮指下一次成功刷新可见，不另加 WebSocket。
3. 正常情况下每 300 秒重排展示，按总分降序；同分按首次待处理时间升序，再按稳定事件 ID 升序。时间未知的事件在同分比较时排在有真实时间的事件之后。
4. 确认、拒绝或配置提交成功，立即刷新受影响事件；已解决事件移除并用当前最高分候选补位，不让老板等五分钟。
5. 未解决但改变了阶段的事项，显示该阶段实际可用的下一步动作。例如核验执行后仍有未决费用，不能将整件事误标为全部完成。
6. 卡片正在编辑或请求结果未确认时，五分钟重排暂缓，不移动或挤出当前卡片；结束编辑或确认请求结果后执行最近一轮排序。页面始终最多 3 张卡片。这是保护老板输入的明确交互例外。
7. 其他事件通过「其他待处理（N）/ Other pending items (N)」入口查阅，首页不展开第 4 张卡片。查看不代表处理，也不清除事件。
8. 后台标签页恢复可见时重新读取事实；若已过重排时间，执行一次最新排序，不补跑一串历史排序。

排序不启动任务、不调用模型、不执行审批、不解除费用预留。读取失败时标记数据过期，不能把事件从队列中清空。

## 6. 每张事件卡片的交互

卡片固定包含：**具体事项标题、需要老板决定的原因、影响和当前状态、可操作区域、处理结果或错误**。标题应指明事项，例如「商业化调研：调用结果未明」，不能只留泛化的「目标需要处理」。

显示「重要度 38/100 / Priority 38/100」，展开可查看各因素依据。该数值只表示事件排序优先级，不是任务进度或成功率。

主要操作直接显示。长说明、回执、执行记录可以在原卡片内展开，不能要求老板先打开另一个总恢复窗口才能处理本事件。

| 事件类型 | 卡片内输入与操作 | 服务端确认后的推进 |
|---|---|---|
| 计划审批 | 展示具体计划及授权范围；「批准 / Approve」「拒绝 / Reject」；可填写修改要求 | 批准后按现有预算及公司开关派工；拒绝后该计划不执行；修改要求生成待核对的新版本，不沿用旧审批 |
| 招聘审批 | 展示角色、原因及影响；批准、拒绝、补充要求 | 批准后建立获准执行者并解除对应资源等待；拒绝不创建执行者，不停其他任务 |
| 交付验收 | 原卡片查看实际交付物、输入不通过原因；「验收通过 / Accept delivery」「退回修改 / Request changes」 | 通过后结案；退回后记录具体要求，进入修订流程；不能仅因点击通过伪造交付证据 |
| 已知失败或无进展 | 展示失败步骤；输入调整要求；「继续此任务 / Continue task」「停止此目标 / Stop goal」 | 只推进或停止关联工作；范围变化需重新核对授权；保留历史费用和产物 |
| 未知执行及费用 | 展示该事件关联的执行、调用和预留；输入核验依据；按选择显示用量、费用或放弃结果字段 | 执行核验与费用对账分别保存；满足条件后在原卡片提供继续任务，不重放未知外部动作 |
| 金额预算 | 复用 Token 数量、单价和计算后 CNY 金额表单；「保存公司预算 / Save company budget」 | 保存后解除相应额度等待；公司为 OFF 时仍不自动开机 |
| 只收款配置 | 选择支持的链，填写公开收款地址；「启用只收款 / Enable receive-only payments」 | 后端校验保存，实际配置满足后解除相关配置等待；不接受钱包私钥 |
| 需受控模型或软件配置 | 显示缺失项、填写配置变更要求、提交相应受控变更请求并重新核验 | 使用既有受控配置或发布流程；检测到实际条件满足才解除事件，不把「已处理」按钮当成配置成功 |

「填写详情」必须写入关联事项并影响下一步处理，不能只在前端暂存一段无处使用的文字。审批备注与修改授权内容应区分：修改了实际计划或范围，需要新版本及新审批绑定。

### 原未知调用的卡片必须能这样处理

- 显示关联目标、未知结果及实际预留 **516 微元，即 0.000516 CNY**。
- 「核验费用 / Verify charges」：填写真实已核验用量、费用和回执依据，提交该调用的结算；不能自动填 0。
- 「确认并停止结果未明的工作 / Acknowledge and stop uncertain work」：填写核验依据后，仅放弃该未知执行结果，未决费用继续预留。
- 执行结果已核验、且允许继续时，原卡片显示「继续此任务 / Continue task」；老板明确点击后才按现有公司开关、预算和权限启动后续工作。
- 如需停止关联目标，提供「停止此目标 / Stop goal」；停止目标不能抹去未决账单。
- 每个按钮清楚说明会推进什么。费用结算不等于交付完成，放弃结果也不等于自动重试。

## 7. 提交、失败与草稿

- 每次决定绑定具体事件、业务实体及当前 revision/hash，服务端校验真实状态和允许动作。
- 点击后显示「提交中 / Submitting…」，禁止重复点击；提交期间不因轮询改变本次请求字段。
- 超时或连接断开显示「结果待确认 / Result not confirmed」，保留完整原请求和幂等键，提供「重试原请求 / Retry original request」。不能换一个键偷偷执行第二次。
- 服务端明确拒绝或业务版本已变化时，保留老板输入，展示具体错误及最新事项，重新核对后再提交。
- 输入草稿按实例、事件 ID 隔离；展开、折叠、五分钟排序和语言切换不清空输入。未知请求结果不得只因关闭卡片或刷新而遗忘。
- 普通业务草稿可按现有模式保留；密钥不得进入聊天、日志或浏览器持久草稿。
- 提交成功后以服务端返回的状态显示结果并刷新事件；不会在响应到达前先标记成功。

## 8. 最小实现范围

1. 在现有 overview 上补齐事件事实、明确可用动作及评分依据；评分采用纯函数，不增加数据库、消息中间件或另一套任务权威。
2. 重构现有 `AttentionMessage` 为按类型组合的原卡片操作区域，复用审批、预算、收款及单条恢复表单。
3. 为当前确实缺少的「退回修改、补充要求、继续或停止关联工作」补齐实际命令；只接受明确允许的字段并保留现有幂等、revision/hash 校验。不能让任意详情输入变成无限制执行指令。
4. 把五秒事实刷新与五分钟展示排序分开；保留全部候选事件、未决请求和输入状态。
5. 页面新增或变更的标题、按钮、字段、状态、说明及错误同时实现中文和英文；上述中英按钮名称是两种语言的对应文案，不是同时显示两套按钮。
6. 顶部三个指标、公司手动开关、商城付款和 8766 发布职责保持现有边界。

## 9. 验收标准

1. 生成超过 3 个待处理事件，首页始终最多 3 张；其余仍能查询，处理一项后正确补位。
2. 每种事件都有有效的确认、拒绝或输入入口；提交确实改变关联业务状态，不只关闭卡片。
3. 本次真实未知调用可在原卡片核验、放弃结果、按条件继续或停止目标；保留未核验费用，不影响独立任务。
4. 逐项验证五个因素的分值、边界、满分和同分排序；普通轮询不重排，五分钟到期自动排序，未显示的事件同样更新评分。
5. 编辑或未决提交期间不会丢失输入或换卡；结束交互后执行最新排序。页面恢复可见时只执行一次需要的重排。
6. 双击、超时、响应丢失、刷新、重排和版本冲突，不产生重复审批、费用结算或任务执行。
7. 拒绝或退回按各自业务含义推进；不能统一当成「已完成」，也不能因为拒绝一件事暂停整个公司。
8. 同一事故只占一个席位；同一目标的不同待审批事项仍全部可处理。
9. OFF 不因处理卡片或追加预算自动变为 ON；外部动作 UNKNOWN 不因选择继续而无条件重放。
10. 中文、英文及 390×844 移动布局均核对全部卡片字段、禁用条件、提交错误、未决重试和排序行为。

验收应包含评分函数测试、组件交互与计时测试、实际 API 状态核对及浏览器核对。涉及计费执行时使用有上限的内部任务；支付回执测试与真实链上付款分开记录。

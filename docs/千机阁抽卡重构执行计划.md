# 千机阁「观星台点将」执行计划

> 2026-09-28；依据《千机阁抽卡重构策划案.md》与本地代码核对。代码基线：`0bd7992`。
> 本文保留原执行计划；实际执行与验证结果见第 6 节。原策划案和工作区数据未修改。

## 1. 目标与成功标准

每次产生新的千机身份，都有一份可追溯的八维抽卡事实；用户可用钦点、GitHub 访贤、千机随机三种模式抽取候选，之后沿用现有试炼和 Owner 终审。运行时繁殖产生的千机也必须拥有抽卡事实。人物卡先能展示数值、叙事与待绘状态，再补图像和展示效果。

完成 P0 的判据：

1. 单抽、十连、试炼候选建立、运行时繁殖都写入同一格式的抽卡事实；同一请求或出生 effect 重试不多抽，Owner 抽卡不重复计保底。
2. 8 维均为 0.5–2.0 的一位小数；稀有度与已保存八维的均值区间一致；给定算法版本、seed、抽卡通道和抽前保底计数可复算数值。
3. 三种来源各能生成一人。GitHub 师承只能指向创建时实际验证过的公开仓库；失败降为随机时，保留原请求模式与失败原因。
4. 试炼仍按现有 2–3 人、相同规则串行执行，由 Owner 选择录用者；抽卡事实不因正式／试炼人设切换而改变。

P1 完成后，观星台可操作、卡片可展示完整属性和 prompt；图片可以暂为“待绘”。P0 已完成落选归档，P2 完成后可从英灵殿和图鉴集中查到。

## 2. 已确认的规则修正

### 2.1 稀有度与八维算法

原策划案的 `1.0 + N(0, 0.28)` 独立抽八维，再以均值判稀有度，无法得到所写的 SR/SSR 概率。改为先抽档位，再抽八维：

- 基础档位概率：N 35%、R 45%、SR 15%、SSR 5%；这是**保底介入前**的概率。
- 每次抽取使用持久化的 32 位无符号 seed 和固定版本的伪随机算法。先从所抽档位选定目标总分 `S`（单位为 0.1）：N 取 72–83，R 取 88–107，SR 取 112–131，SSR 取 136–148，各区间内均匀取整数。
- 以 `S/80` 为中心，为八维各生成标准差 0.28 的噪声，先钳制并取整为 5–20 的整数分；再按 seed 洗牌的维度顺序逐个加减 1，直到八维整数分总和为 `S`。目标总分始终在可行范围内，因此修正必定有限步完成；最终每维除以 10 存档。
- 档位阈值保留：N `<1.05`；R `[1.05,1.35)`；SR `[1.35,1.65)`；SSR `≥1.65`。**只用已存档的一位小数八维求均值**，不对均值二次四舍五入；所选 `S` 保证结果落在目标档位。
- 抽前连续 9 次无 SR/SSR 时，第 10 抽若原档位为 N/R，则提升为 SR；原档位若是 SSR 则保留 SSR。抽后 SR/SSR 归零，否则计数加一。保底覆盖后实际 SR 占比会高于 15%。
- 保底只计入 Owner 主动单抽／十连，运行时繁殖只按基础概率抽取，不消耗或重置 Owner 的保底。服务端按事务中的顺序逐张更新 Owner 计数器，十连的数值与计数器一次提交。

这替换了“最终八维相互独立”的旧表述。每张卡仍有八个有波动的分值，稀有度分布、数值范围和复算性可以同时成立。

词条按最终值计算：任一维 `≥1.8` 得天赋，`≤0.6` 得短板。相同最高属性组合可以复用意象；不建“已使用意象池”。最高属性或次高属性并列时按固定的八维顺序打破平局。

### 2.2 身份、载体与审计边界

- 抽卡生成的是千机身份。Owner 单抽／十连先生成未绑定的 `candidate` 档案；进入试炼时才指定未使用坐标、初始能量并绑定 Pixel。运行时繁殖则在出生事务中直接抽卡、建档、绑定。这样不创建“只为展示而存在的假 Pixel”。
- 抽卡事实与可编辑人设分开保存。现有 `narrative.traits` 只接受 0–1，不承载 0.5–2.0 八维属性。姓名、小传、行为指令可保留现有 revision；属性、稀有度、seed、来源证据和指纹不通过 `PUT /qianji/:id/narrative` 修改。
- seed 只复算**数值**。模型小传、GitHub 搜索结果、图片不是 seed 的纯函数；必须保存当时的输入、已核验仓库链接、输出文本、prompt 全文与生成结果，才能审计。
- 图片沿用现有 `assets/qianji/<qianjiId>/<内容哈希>.<扩展名>` 及画像接口。原案的 `live/portraits/{pixel_id}.png` 会在同一坐标重生时冲突，不再另建一套存储。
- 实际稀有度只作人物展示，不改变模型权限、工具清单、能量或试炼预算。

## 4. 执行顺序

### P0-1：抽卡事实与纯算法

1. 在 `packages/protocol` 定义八维固定键序、档位、词条、抽卡事实、来源和生成状态；`QianjiProfile` 对旧档案允许缺少抽卡事实，但所有新出生入口必须写入。
2. 在 `packages/domain` 增加纯抽卡函数：seed → 档位 → 八维 → 均值校验 → 词条 → 排序／平局规则 → 指纹输入。固定 PRNG、正态采样及算法版本，禁止依赖 `Math.random()` 复算。
3. 在 `packages/persistence` 新增小型 `qianji_draws` 表，按 `qianji_id` 关联档案，存不可编辑的数值事实与唯一抽卡指纹；lineage、生成状态、卡面 prompt 和 prompt 指纹允许由限定的完成操作补写，不能借此修改数值。抽卡指纹与 P1 的 prompt 指纹分开，后者尚未生成时可为空。另设单行 `gacha_pity` 业务表保存 Owner 保底计数。Repository 提供事务内创建、查询和限定字段补全，不暴露任意改写抽卡事实的方法。原有 SQLite 建表入口要可重复运行。
4. 抽卡、计数器、千机档案、事件与 Owner 幂等结果在同一 SQLite 事务中提交。十连中途失败则全部回滚。随机模式可在事务内完成基础叙事；需外部调用的模式先落数值事实，再在事务外生成叙事并写入结果或明确失败状态，避免在同步数据库事务里 `await`。

验收：固定 seed 的金样本一致；所有结果都满足整数总分、档位、范围与词条规则；用受控随机输入验证 35/45/15/5 档位边界，再以固定的大样本检查保底前比例，允许事先写明的统计容差；十连失败回滚与并发请求不重复计数。20 抽只验字段与流程，不要求必出 SSR。

### P0-2：三种叙事来源和抽卡 API

1. 新增 `GachaService` 与 `POST /api/gacha/draw`，请求包含 `count: 1 | 10`、`mode`、该模式允许的输入和 `idempotencyKey`。初版十连只支持千机随机；钦点和 GitHub 访贤仅支持单抽，避免一份人设同时生成十个同名人物和单请求内十次外部调用。服务端校验未知字段、长度、数量与重复请求。
2. 千机随机：本地姓名池、职位池和小传模板；繁殖也复用这一模式。钦点：姓名可空、职位和一句话人设必填；模型只负责扩写小传、缺陷、行为指令、口头禅，属性冲突要写成故事，不改数值。
3. GitHub 访贤：用公开 GitHub 搜索接口按职位找候选仓库；读取并验证选中仓库信息／链接后提取 3–5 个可溯源技能标签。保存原请求模式、最终 `origin`、仓库链接和查询时的证据；搜索不到或失败时按原案降为随机并写明原因。仓库文本视为不可信资料，不能让它改写抽卡规则或服务指令。
4. 钦点／访贤先提交数值事实，再返回 `pending`；同一服务进程在事务外启动生成，不为 P0 新建通用队列。增加按卡查询状态的只读接口和同卡重试入口，前端据此刷新；进程中断留下的 `pending` 也能由用户重试，不重新抽数值。叙事模型调用使用现有文本模型配置；记录调用结果及用量／成本，不从尚未绑定的 Pixel 扣能。模型失败要留下可见的失败状态，不能吞错。

验收：三种模式各成功一次；同 key 重试返回原卡；同 key 不同请求冲突；受控 GitHub 响应测试只接受已验证仓库、拒绝虚构链接；真实网络可达性作为单独集成验证，不作为本地单测的通过前提；无模型配置时钦点明确失败，随机模式仍能完成。

### P0-3：试炼和繁殖接入

1. 扩展 `POST /api/trials/:id/candidates`：新增接受未绑定、未参加其他试炼的 `qianjiId`，以及坐标、初始能量和幂等 key；原有请求格式暂时保留，但内部必须补抽卡事实，不能再创建空白候选。复用现有 staging、坐标检查、账户、binding、预算和 execution 创建；正式人设以抽出的档案为准，试炼人设只作运行时变体，卡面依正式人设构建，二者都不能覆盖抽卡事实。P0 前端提供简洁的“抽一人并加入试炼”入口，P1 再做完整观星台页面。
2. `effect_runtime.ts` 的出生路径从 `effectId` 稳定推导 seed，在现有繁殖事务中完成随机抽卡事实、千机档案和 binding；效果回放不能新建第二张卡，也不改变 Owner 保底。外部模型写作与生图不得放进繁殖事务；初版用本地模板即可。
3. Owner 终审时，落选者除转为 `retired` 外，还要复用现有退役归档边界，将其 Pixel 文件和产物移入其 binding 的历史目录，处理失败回滚；取消试炼仍按原状态机处理，不把取消当落选。
4. 落选或正式退役后，现有 `PUT /qianji/:id/narrative` 和画像替换入口不得继续改写该人物；需更正时另行追加有版本的说明。尚缺的首张 prompt／画像可在 P1 按保存的人设 revision 追加一次并留事件，不得覆盖已经陈列的版本。人物数值要影响运行时行为描述时，只将八维和由此得出的叙事摘要加入 `QianjiPromptIdentity` 与 `PromptBuilder` 白名单，保留现有权限、认知隔离和人设 revision 语义。

验收：2–3 名抽卡候选走完试炼和 Owner 终审，落选者已归档；原有候选请求不产生空白身份；重复绑定被拒；繁殖新生和同坐标重生均有独立身份与抽卡事实，旧代仍归档；重试不会重复扣能、重复生成身份或影响 Owner 保底。

### P1：人物卡与图像

1. 在 `packages/domain` 或服务层实现 prompt 构建器：固定风格锚、8 色、职位×最高属性服饰道具、28 个最高属性组合意象、缺陷／天赋神态；同组合可复用，经历与 seed 负责个体差异。保存中文展示文本、英文生图文本、所用人设 revision、模板版本及 prompt 指纹。P0 已有档案只补一次空缺 prompt，不覆盖已有版本；没有必要建意象占用表。
2. 在 `frontend` 增加观星台入口、模式输入、单抽／十连、翻牌与稀有度效果；人物卡展示八维图、词条、来源、师承及“待绘”。交互以已持久化的结果为准，刷新后仍能看到同一张卡。
3. 对接图像生成接口并把结果写入现有画像资产路径；状态至少区分待绘、生成中、已完成、失败，失败可对同一人物补图，不重新抽卡。保留现有手工上传能力。图像供应方和实际付费调用在本阶段单独配置与验收。

验收：8 色与 28 组映射齐全；同一输入产生同一 prompt 指纹；有图／无图／失败三种卡面可展示；画像读取仍通过现有接口。

### P2：英灵殿、历史与图鉴

1. 扩展现有退役人物档案页，展示抽卡事实、来源、卡面和已在 P0 建立的落选／退役归档履历。
2. 新增独立的 `GET /api/gacha/history`，按创建时间／ID 分页查询抽卡历史并计算图鉴统计；保留现有 `GET /api/qianji` 的响应结构，避免影响运行时和组织桌面的读取。收集度以已保存的真实抽卡记录计算，不把仅有旧身份的资料算成抽卡结果。
3. 英灵殿按 P0 已冻结的退役快照展示；后来的人设更正只追加说明，不覆盖原抽卡事实或旧卡面 prompt。

验收：落选、正式退役、同坐标重生三类人物均可追溯；分页超过 200 条无丢失和重复；已归档人物的抽卡事实不能被现有编辑 API 改写。

## 5. 阶段验证与边界

- 每个 P0 子阶段完成后跑对应 domain、persistence、server、runtime 测试，并运行根目录 `pnpm.cmd build`、`pnpm.cmd test`。P1/P2 增加 `pnpm.cmd --dir frontend build` 和前端定向测试。命令在 Windows PowerShell 执行。
- 概率验收用可复现的大样本，不以 20 抽有无 SSR 下结论。外部 GitHub、真实模型与生图的验收要和 mock／本地单测分开报告；真实调用产生的费用单独记录。
- 不重清数据库，不自动修改原策划案，不重写现有试炼、Pixel 能量和调度机制。若实施时实际代码与本计划入口不符，先核实差异，再只调整受影响任务。
- 执行时先做 P0；P0 验收通过后再进入 P1，最后 P2。每阶段报告已完成项、验证结果和未完成项，不把后续阶段占位写成已实现。

## 6. 执行结果（2026-09-28）

- P0 已接入纯抽卡算法、SQLite 事实与 Owner 保底、三种来源、试炼绑定／落选归档、繁殖出生；保留旧候选请求兼容并补抽卡事实。
- P1 已接入组合式人物卡 prompt、观星台与卡面、可选画像接口和原卡失败重试；还支持浏览器本地图片上传及公开网络图片 URL 导入。导入复用原画像资产校验与内容哈希路径，网络下载限制公开地址、图片格式和 2 MiB。画像只在用户点击后请求；需配置 `GACHA_IMAGE_API_KEY`、`GACHA_IMAGE_MODEL`，可选 `GACHA_IMAGE_BASE_URL`。
- P2 已接入独立历史分页与真实记录统计，并在英灵殿陈列落选／退役人物的抽卡事实、来源和存档卡面。
- 本地验证：`pnpm.cmd build`、`pnpm.cmd --dir frontend build`、`pnpm.cmd test` 通过；全量 55 个测试文件、344 项测试通过。覆盖算法金样本与概率、十连回滚、幂等、GitHub 受控仓库响应、画像失败重试、本地／网络图片导入与内网地址拦截、试炼归档、210 条历史分页。
- 尚未进行真实 GitHub、网络图片 URL、文本模型与付费生图联调；本地测试使用受控响应。未重置工作区数据库，未发起付费调用，未部署。

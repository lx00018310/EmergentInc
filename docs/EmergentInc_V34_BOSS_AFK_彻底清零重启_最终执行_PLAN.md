### 1.1 本次删除范围（彻底归零）

### 1.2 破坏性重置命令：显式触发，删除后全新初始化

1. 本地 AI 先读取 `AGENTS.md`、当前 Git 状态及 `scripts/launch-approved.mjs`、`.env` 中实际工作区配置，**找出唯一旧实例实际使用的 workspace 路径**；不能假设一定是仓库根下的 `workspace`。列出全部实例数据路径及清理范围。
2. 停止主服务 `8765`、升级服务 `8766`、后台 Worker、自动调度器、支付监听；验证旧实例无进程打开 DB、WAL 或工作区文件。若仍运行则拒绝删除。
3. 编写**独立、一次性、仅按指令执行**的 `scripts/v34-reset-workspace.mjs`，默认行为为只读预览：列出精确规范化路径、将被删除的文件数/总大小、特殊危险后果、将初始化的 V34 目录；不拷贝旧数据。
4. 删除前做硬性路径校验：规范化 `realpath`；拒绝磁盘根、用户 Home 根、仓库源码根、系统目录、空值、遍历路径、符号链接指向仓库/外部目录、工作区与源码互为父子等危险目标。对于 workspace 在仓库内的常见情况，必须只删除经过精确识别的 `workspace` 目录，不得把父级源码一并删除。对路径别名/链接一律 fail closed。
5. 只接受 `--workspace <绝对路径> --destroy --confirm "DELETE-BOSS-AFK-V34:<实例目录规范化路径>"` 之类**同时包含显式破坏标志和绑定目标路径的确认文本**。命令打印完整目标路径，再执行直接文件删除；禁止回收站、临时存档、隐式 rename 备份、快照、旧版二次保留。不要为确认流程添加多轮人工问答；用户已经同意清零，CLI 单次显式执行即可。
6. `--destroy` 只操作当前实例，不能误删其他项目、其他 EmergentInc 部署及 V34 已初始化的新实例。若发现 `workspace-format.json` 标识 `format=34` 且有新业务记录，则拒绝执行（除非将来另行设计有独立批准的新 V34 重置功能；本版不做）。
7. 删除成功后立即执行**全新 V34 初始化**，建立空目录、全新数据库、`workspace-format.json`（例如 `{ "product":"BOSS-AFK", "format":34, "initializedAt": ... }`），再启动新服务。新的系统 ID、Goal/Task ID、预算修订等必须来自新实例，不能继承旧数据。初始 Company `OFF`、预算未授权、收入 0、没有商品销售回执。
8. 如果删除后初始化失败，只报告**新的初始化失败**并允许重新从空目录初始化；**不恢复旧实例、不创建旧数据的备份、也不声称数据可回滚**。程序源码 Git 回退与新实例之后的安全升级回滚是另一回事。
9. reset **绝不**挂载到 `pnpm install`、常规启动、`git pull`、版本升级、server 启动钩子；开源用户正常升级不触发销毁。只有本次显式命令能清空指定旧实例。

**推荐命令约定（最终以代码实现的精确 CLI 参数为准）：**

```bash
# 仅预览，不做备份，也不删除
node scripts/v34-reset-workspace.mjs --workspace "/absolute/path/to/workspace" --dry-run

# 一次性不可逆销毁，并创建全新 V34 空工作区
node scripts/v34-reset-workspace.mjs --workspace "/absolute/path/to/workspace" \
  --destroy --confirm "DELETE-BOSS-AFK-V34:/absolute/path/to/workspace"
```

**要求：不能用“新建 workspace_v34、旧 workspace 留在原地”冒充清零。旧实例物理目录必须删除，之后在原目标路径创建 V34 新空工作区。** 若当前 OS 未能删除文件，要失败报告并禁止启动混合新旧目录，不能静默跳过。

## 3. 新版最小状态机（允许彻底替换旧的）

### 3.1 不再让三个/四个旧经营 FSM 并行

只保留这几个直接支撑真实经营与安全的数据事实：

| 实体 | 最小建议状态 | 作用 |
| --- | --- | --- |
| Company | `OFF / ON / PAUSED_ERROR`（请求状态与观测状态仍需区分） | 老板关闭后跨重启不能自启；错误/费用未决可阻断派工。 |
| Goal | `ACTIVE / PAUSED / COMPLETED / STOPPED / BLOCKED` | 长期经营目标，可暂停/删除（删除采用终止 + 不显示，审计结果不抹除）。 |
| Task | `READY / RUNNING / WAITING_DECISION / BLOCKED / DONE / FAILED` | 任务独立生命周期、唯一 ID、依赖关系、执行凭据。 |
| Decision | `PENDING / APPROVED / REJECTED / EXPIRED / RESOLVED` | 关键待办、授权目标、hash/revision、幂等操作。 |
| ModelCall / ExternalOp | `RESERVED / SENT / CONFIRMED / UNKNOWN / RECONCILED` 等必要精确状态 | 资金授权与未知结果的防重试、防重扣。 |
| Order / Payment | 原有严谨收款与最终性状态，或精简后**等价**完整状态 | 不能把区块链“发起”“确认”“最终收款”合并。 |

**注意**：以上是新业务层契约示意，不是要求机械地一比一替换所有底层运行库。数据库层约束与工具调用可能需要更细的内部状态；基于真实恢复需求保留，且不得混同 Goal/Task 的对外状态。

### 3.2 精简不等于删除安全与确定性

任何付费、外部发布、下单、转账、修改 Git 源码、发布升级等敏感操作保留：**来源身份、作用域授权、签名/Hash 或 revision、幂等键、费用预留与结算、外部结果 UNKNOWN、可追踪证据、自动失败回滚**。

老板已经明确批准某一个目标或站内商品动作，可在授权范围内自动执行；未经授权的外部发帖、钱包/支付设置变更、软件发布、超预算不能因“简化”而自动完成。

### 3.3 两类记忆足够

- **Current**：当前目标、当前 Task、近期上下文与未决决定。
- **Knowledge**：确实验证有效的 Skill、工具、交付模板与知识；可复用、可审查来源。

## 6. “三消息”注意力调度器（V34 真正的新核心）

### 6.1 消息来源与级别

候选只从**真实持久化记录**产生：

1. `Decision`：最新待审批提案、招聘/资源决定、明确超预算、支付方式变更等授权请求。
2. `Critical`：UNKNOWN 模型/外部操作、异常账单、数据库/运行恢复、收款核验异常、公司被阻断。
3. `Milestone`：首款商品核验上架、首笔实际收款、关键目标完成、有证据的交付物。
4. `Strategic`：真正影响经营方向且有证据的建议；第一期只从已落库的 Goal/Task/评价事件生成，不让 LLM 直接发自由文本“高优先级通知”。

优先级默认：不可忽略的 Critical → 待老板执行的 Decision → 重大 Milestone → 普通结果/建议。相同业务实体去重，稳定 ID，按优先级、时间、ID 决定顺序。

### 6.2 生命周期

- `PENDING_DECISION`：在 Owner 作出决定、请求失效或事实已由其他途径解决前，不能被新消息挤掉后遗忘。
- `ACTIVE_BLOCKER`：直到后台确认问题解除或人工正确核验才消失，不以刷新次数判断。
- `MILESTONE`：新结果短期可见；被更重要消息替换后写入 **V34 新实例**的事件日志，不能伪装为实时事件。
- `RESOLVED`：成功操作完成后的旧消息立即出列，榜单补入下一条。
- **列表 0～3 条**；如果有更多未决事项则出现“另有 N 项待处理”的文本统计，不添加第四张消息卡。点击统计可用本页暂态小弹层查看其余必须处理的事项，**不开发完整‘视察公司’页面**。
- `ALL_CLEAR` 时显示“目前无须你处理，公司正在按目标工作”；不要生成虚假的三条消息。

### 6.3 待办必须可以在首页处理

- 决策卡必须有：人话标题、为何需要老板、批准/拒绝后具体影响、必要成本或风险、对应证据链接、批准/拒绝/更多详情。
- 复用或提取现有 `CompanyProposalCard`、`OwnerInbox`、`OwnerActionCard` 的**真实提交与审批逻辑**，不是复制 JSX 后做假按钮。交易级关键动作保持 hash/revision/idempotency 和重复提交防护。
- 旧预算看板删除，但**首次公司预算授权/额度不足时必须从 Boss 页的消息中打开安全的金额配置对话框**，复用 `OwnerBudget` 真正的请求协议，不能要求去尚不存在的“视察公司”。
- 点击“批准”成功后必须等接口确认，再刷新读实际状态；失败/UNKNOWN 明确展示并保留原待办，不能先移除。
- 长文建议、策略执行、继续/暂停某 Goal 可以通过底部唯一对话框处理；不创建“目标/任务管理”独立导航。
- 不能让历史聊天文本或 Skill 内容伪装成 Owner 的新审批。聊天处理要检查实际登录用户权限及明确的当前意图。

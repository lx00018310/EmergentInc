# EmergentInc：AI 创业矩阵定位与首笔外部收入计划

日期：2026-09-22  
状态：定位建议与实施计划；已根据 Owner 补充加入开源仓库与服务器业务的循环；本轮仅更新本文档，尚未改写 README、业务代码、运行心智或配置，未发布、收款、部署。  
本轮目标：让 Pixel 围绕 EmergentInc 自身制作并推进营销，将开源仓库访问引向真实首发业务，获得首位真实外部用户对 1 元首发体验的付费并完成交付，再将可公开的案例与产品改进反馈回仓库。  
待决项：1 元资格最终对应本地预览版还是托管体验，以及交付日期。当前沿用 Owner 口述的“首发优先体验资格”，不替 Owner 承诺具体交付形式。

逐项实施入口：[Luna max 执行计划](./EMERGENTINC_FIRST_REVENUE_EXECUTION_PLAN.md)，包含任务依赖、允许修改的文件、操作步骤、验收及续接记录。本文件保留业务定位与范围，执行状态维护在执行计划中。

## 1. 对定位的判断

方向成立，但要让包装对应真实的产品机制、当前能力和付费权益。

用户想获得的变化是：从亲自逐项操作 AI，逐步转向提出商业目标、提供资源、观察执行、作出经营决策。产品愿景是帮助用户建立业务、获得收入。当前尚没有证据证明使用系统必然赚钱，也没有证明元胞必然形成稳定有效的组织。

“AI 老板”适合表达用户身份；“AI 创业矩阵”适合表达产品形态；“元胞会社”保留项目自身识别。建议三者分工如下：

| 层级 | 建议表达 | 用途 |
| --- | --- | --- |
| 产品名 | EmergentInc 元胞会社 | 长期品牌，保持现有项目名 |
| 产品描述 | 探索自组织协作的 AI 创业矩阵 | 解释产品机制与方向 |
| 首页主标题 | 做 AI 的老板，从第一笔生意开始。 | 连接目标用户的期待 |
| 首页说明 | 提出商业目标，设定预算与权限，让 AI 元胞尝试形成分工、产出交付物，并根据真实客户反馈推进业务。 | 说明操作方式，保留实验性质 |
| 首发商品 | 1 元首发优先体验资格 | 说明这次付款购买什么 |
| 首个案例主题 | 这套 AI 创业矩阵的第一项业务，就是为自己的首发找到第一位付费用户。 | Owner 已认可的首发任务表达，不表示任务已完成 |

“黑客帝国式矩阵”只作为内部视觉灵感：晶格、节点、通信、能量变化、可观察的控制界面。对外主要解释用户能做什么，不依靠电影联想解释产品，也不把代码雨等视觉包装当成新增产品功能。

### 1.1 能成立的差异与需要验证的主张

当前代码的机制特点是：Pixel 身份不预置职业；心智与交付物长期积累；通信受到局部邻域约束；模型调用消耗 Energy；工具执行受到权限限制；Owner 可提供目标、事实和预算。

可以将“允许分工逐步形成”作为设计方向。不能将“已经自主形成高效公司”“已经自主盈利”“每个人都能靠它创业成功”当成当前事实。

用户设定目标、预算和现实权限，与 Pixel 自行形成工作方式并不冲突。用户如果逐个指定 CEO、销售、工程师，并规定每一步流程，该次体验就应描述为人工编排协作，不能作为自发组织的证据。首轮不新增强制岗位、组织架构或职级字段。

### 1.2 同类检索后的判断

- [MetaGPT 官方项目](https://github.com/FoundationAgents/MetaGPT)：明确包含产品经理、架构师、项目经理、工程师等角色及 SOP。
- [ChatDev 官方项目](https://github.com/OpenBMB/ChatDev)：当前提供可配置的多智能体工作流与团队协作能力，不能简单概括为只能固定角色。
- [AI Town 官方项目](https://github.com/a16z-infra/ai-town)：提供可部署的 AI 社会互动环境。

因此，“多个 AI”“AI 公司”“用户做老板”本身不是足够的差异。EmergentInc 应重点验证并展示：在局部信息、有限心智、有限资源下，分工如何产生或失败，以及这些行为能否推进真实业务。此处是定位假设，不是市场已认可或技术领先的结论。

### 1.3 开源仓库与真实业务的循环（本轮必须完成的路径）

Owner 补充确认：开源仓库是产品介绍、技术验证和获客入口；服务器上的首发业务是这套系统服务真实客户的第一个应用。两者应属于同一个产品故事，真实业务要确实使用 EmergentInc 推进。

```text
开源 README：定位、演示、首发业务入口
  → 外部用户访问服务器上的商品页，咨询或购买
  → EmergentInc 接收目标与反馈，Pixel 产出营销、答复和交付材料
  → Owner 执行尚未接通的现实操作，核验到账与交付
  → 脱敏案例、使用反馈、必要的代码与文档改进回到仓库
  → 更新 README 与业务页，供下一批用户了解和体验
```

闭环必须同时满足以下要求：

1. **双向可达**：README 能到达真实业务页；业务页能回到公开仓库与相关案例。未部署时如实标注状态，不填虚构链接。
2. **实际使用自身系统**：至少一项对外使用的营销或交付材料由 EmergentInc 运行中的 Pixel 生成，并能追溯到相应任务、artifact 和执行记录。由外围开发助手写完全部材料、再贴一张运行截图，不算满足这一项。
3. **反馈进入系统**：真实咨询、购买和使用反馈经脱敏后进入 Pixel 可见的外部输入；至少产生一次有依据的文案、FAQ、交付说明或产品改进。
4. **结果回到仓库**：整理一份可公开的简短案例，关联实际产品版本、Pixel 产物、人工参与、付款/交付状态及限制；README 和业务页都引用它。
5. **下一轮可复用**：下一批用户能看到上一轮产生的更清晰说明、案例或实际修复，不需要重新讲述整个项目。

首轮可以由 Owner 人工发布、接单、转交反馈与核验付款，不新增自动 Git 提交/推送或营销中台。公开页面与运行实例通过实际任务和结果关联，不能仅部署一份静态广告就宣称已运行在线 AI 业务。管理后台不因此直接开放给公众。

完成一次上述循环，可称为“首个业务闭环”；只有后续出现持续的访问、使用、贡献或付费增长，才有证据表明形成了增长飞轮。收入可由 Owner 决定投入下一轮运行或产品改进，不自动转为 Energy，也不据此宣称系统已经自给自足。

### 1.4 README 首屏的具体改动要求

README 更新列入实施任务。以下两句是 Owner 已认可的文案，放在技术架构之前：

> **做 AI 的老板，从第一笔生意开始。**
>
> 这套 AI 创业矩阵的第一项业务，就是为自己的首发找到第一位付费用户。

首屏顺序：产品名与 AI 创业矩阵定位 → 上述文案 → 一段解释用户如何设定目标、预算和权限 → 真实演示/案例 → 首发体验入口与本地运行说明入口 → 当前阶段与能力限制。保留现有技术文档和上手说明，不整篇重写。

业务页沿用同一定位、权益和案例状态。首次发布前核实公开仓库 URL、实际开源许可与发布范围、业务 URL，以及仓库版本与演示版本的对应关系。尚未核实的内容列为待完成，不声称已经上线或开源发布完成。

README 中“当前 VPS 只有密码，因此工具不注册”属于旧工作区状态；实施 README 更新时改为工具准入规则和查看实际状态的方法，避免把某次 Owner 环境的状态当作产品永久能力。可公开案例是经过选择、脱敏的产品文档；原始运行日志、数据库、凭据和私人工作区仍不进入仓库。

## 2. 本轮商品、客户与成功标准

### 2.1 谁最适合首发

首批面向：已经尝试过 AI 工具、对独立开发或一人业务有兴趣、愿意参与早期产品验证的人。不要用“无需任何投入即可稳定赚钱”吸引期待被动收入的人。

首发只验证一种付费动机：用户想亲自尝试经营一套 AI 元胞系统，并愿意为提前体验支付 1 元。

### 2.2 1 元卖什么

按 Owner 原意，商品为“首发优先体验资格”。正式收款前必须补齐一份简短商品说明：

1. 交付形式：本地预览版或托管体验，确定一种。
2. 用户具体能做什么：至少能够提出一个目标、观察实际运行、查看产物和已知限制；不能只有排队编号。
3. 交付时间：写明可执行的日期或时间窗口，不能只写“敬请期待”。
4. 额外成本：若为本地版，明确模型 API 和运行环境由谁提供；若为托管，明确体验预算与使用次数。
5. 支持范围：明确包含的上手说明和反馈入口，不默认附赠长期人工服务。
6. 未交付处理：建议未能按约定交付时退回体验费；联系人与处理方式真实可用。

若交付条件尚未确定，可先展示样例并收集兴趣，不开放付款。1 元不是无限期授权、终身会员、无限模型额度或收益分成，除非另行明确决定并具备兑现能力。

公开源码与付费体验要分别说明：1 元必须对应明确的优先体验、协助上手或托管资源等实际权益，不能仅把公开可获取的源码称作付费专属内容。最终只选择能够兑现的一组权益，当前不默认赠送全部服务。

### 2.3 分开记录四个里程碑

| 里程碑 | 验收证据 | 不代表什么 |
| --- | --- | --- |
| 兴趣 | 真实外部用户咨询或申请体验 | 不代表购买 |
| 首笔外部付款 | 实际到账至少 1 CNY，能关联到首发商品与外部买家 | 不等于已完成体验交付；预付体验费单独标记 |
| 首笔有效交付 | 已提供约定权益，取得使用或接收确认，并记录退款状态 | 不代表可持续商业模式 |
| 后续商业验证 | 更多独立客户、实际使用、继续付费与成本数据 | 不能由一笔 1 元交易推导出来 |

本轮完整验收要求：真实外部客户理解商品后自愿付款，款项可核验，权益如约交付。Owner 自付、安排回款的测试、内部 Energy 转账均不计入。退款另记，不继续当作保留收入展示。

## 4. 实施顺序与验收

### P0：恢复可信的执行与反馈

执行者：Owner/实现者处理代码与真实权限，Pixel 执行授权范围内的验证。

- [ ] 修复已确认的凭据读取缺口；验证现有密钥文件名受保护、正常产品资料仍可读。
- [ ] 对根 Pixel 下达简短事实纠正：最近报错为目录越界，允许根目录是 `/var/www`，认证是否可用仍待验证。
- [ ] 单独执行一次允许目录读取；只有出现真实认证错误时才处理远端授权，不开启 `ssh_exec` 来代替正确配置。
- [ ] 将本地资料读取与 VPS 探测分开；取得各自回执后再安排写入或发布。
- [ ] 在有界 Run 中验证 Mandate 被执行；要求 Pixel 的提醒区分执行回执、历史判断与待验证假设。
- [ ] 若没有新回执、客户反馈或可交付物，不继续增加轮次。保留有效证据，停止相同失败的定期空转。

### P3：由 Pixel 制作首发宣传，并通过一个真实渠道发布

执行者：Pixel 制作；Owner 提供真实发布权限并执行尚无工具支持的动作。

- [ ] 业务页放置公开仓库与案例链接；核对两端的商品权益、版本、付款/交付状态一致。

验收：有一个真实发布链接，且从公开仓库 README 可访问业务页、从业务页可返回仓库；用户能够查看商品、找到卖方并完成约定购买步骤。确认至少一份正式使用的物料出自本系统 Pixel。生成 HTML、SSH 成功或页面部署成功均不能单独视为完成营销。

### P5：根据反馈决定下一步投入

首批建议联系或触达 10 位符合画像的用户；这个数量是试验范围建议，不是已有数据，也不是转化保证。记录实际看过样例、有效询问、付款、完成体验的人数；无法测量的指标写未知，不估造。

| 观察结果 | 下一步 |
| --- | --- |
| 没有真实目标用户看过 | 调整触达方式，不继续润色第 N 版页面 |
| 看过但不理解 | 简化定位，补一份真实操作演示 |
| 理解但不愿付费 | 询问原因，调整权益或客户画像；不能靠“只要 1 元”代替价值 |
| 付款但无法开始体验 | 优先修复交付和上手问题 |
| 能体验但没有产物或行为无法解释 | 优先验证执行可靠性与目标适配 |
| 有人体验后愿继续使用 | 再确定第二批权益、正常价格与必要自动化 |

记录真实模型成本、托管成本与人工投入；1 元是首发试验价格，不据此声称可盈利。

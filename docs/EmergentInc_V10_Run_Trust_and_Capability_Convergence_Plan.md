# V10 运行可信度与能力一致性整改计划

日期：2026-09-17  
基线：`59a359e`（V10.1 FIX）及当前工作区  
目标：先让运行状态、调用结果和账目可信，再让声明的能力与实际执行一致，减少重复读取、反馈放大和 SELF 空转。

## 0. 范围与实施约束

- 本次只列计划，不执行修复、重启、恢复、退款、充值或真实远端操作。
- 当前 `EmergentInc_UI.bat`、`EmergentInc_UI.ps1`、`apps/server/src/main.ts` 存在未提交修改；执行者必须先检查差异，不能覆盖。当前另有未跟踪 `AGENTS.md`，已读取其最小改动原则。
- 不做外部获客/支付实验、不增加元胞、不建立新的任务规划器或消息中间件。
- 本计划仅处理与这两个目标直接相关的恢复与事务边界，不宣称完成全部 V10 Exactly-Once、迁移和架构验收。
- 所有验证先在隔离 workspace、可控 Provider 和工具适配器上执行；当前实验数据仅用于只读诊断。模拟模式不得自动切换到真实模型或写入真实实验账本。
- 不自动清空历史消息、不批量退款、不把未知调用当作失败重跑。任何历史数据修正先形成逐条证据清单，再单独取得执行授权。

## 2. 方向一：先恢复运行可信度

### A1. 只读核查并阻断不安全的新 Run

**实施：**

1. 启动时先取得工作区单进程占用权，再检查旧 RUNNING Run、OPEN 预留、CALLING 消息、STARTED 工具和未完成 Effect；持锁失败不得修改旧 Run。
2. 将“服务进程是否存活”“Run 是否仍有执行者”“供应商结果是否确定”分别判断，不能用端口不通推导退款。
3. 返回恢复摘要：runId/messageId/callId/operationId、阶段、预留、已有响应/回执、阻塞原因和建议核对项。脱敏，不输出凭据和私有文件正文。
4. 没有足够证据确定安全处理的条目保留原始记录并进入 PAUSED_RECOVERY_REQUIRED；阻止新 Run 消费相关工作区的未决任务。查询页面仍可打开。
5. 本期不建设完整自动恢复系统；已有可靠响应可进入 A3 的响应复用路径，其余未决项明确暂停。

**验收：** 正常结束后重启能显示上次真实结果；进程在调用中退出再重启不能显示 READY 或自动再调用；两个实例不能同时修改同一工作区。异常工作区显示具体阻塞 ID，不能只写“需恢复”。

### A2. 分类记录调用结果，不再统一退款重试

**实施：**

| 场景 | 应有结果 |
| --- | --- |
| 已证明请求尚未发出、或供应商明确未执行/未计费 | 按既有规则结算为零/退还预留，保留原因；不无限自动重试 |
| 调用已发出，超时、断连、用户取消、进程退出，无法确认是否计费 | CALL_OUTCOME_UNKNOWN，保留预留与证据，暂停；不能凭网络错误名称退款 |
| 已收到有效 usage，但业务响应不能解析 | 保存原始响应和 usage，结算一次，MODEL_RESPONSE_INVALID；不能当未计费失败 |
| 已保存有效响应 | 复用该响应，不能再次发模型请求 |
| 工具 STARTED 后结果不明或明确返回 UNKNOWN | 保存 UNKNOWN，暂停后续 Effect，不自动重复远端操作 |

- Provider 使用 timeout/abort 原因与请求阶段进行分类，处理请求体发送后和读取响应体期间的异常；不要把所有 5xx 视为明确未计费。
- Stop 后禁止发起下一次模型调用；已经发出的调用按原有协作式边界收尾，不能因统一 AbortSignal 把未知结果转换为退款。
- 保存错误类别、阶段、HTTP 状态（如有）、脱敏消息、时间和关联 ID。Scheduler 透传到 RunService，不能丢失具体原因。
- usage 的零值用空值判断处理，不能通过 `|| 200` 把真实 0 completion_tokens 替换成估值；缺失 usage 不能假称真实用量。

**验收：** 用可控 Provider 分别注入调用前失败、服务端已接受后超时、响应体中断、非法业务 JSON、有 usage 的错误响应和 Stop。逐个检查资金与终态，尤其验证未知结果不退款、不重发。

### A3. 修复响应复用与正常结算最小原子边界

**实施：**

1. 通过稳定 messageId 关联已存在的调用尝试，不能先生成新时间戳 callId 再查询它。保留原 callId；只有明确允许的新尝试才能生成新 callId。
2. 在一笔现有 SQLite 事务内完成正常响应保存、预算结算、账本更新和 RESPONSE_STORED 标记；使用同一连接，不分别提交。
3. 已保存响应的消息复用响应与已完成 Effect 记录；未决外部 Effect 不进入通用重放。没有足够恢复证据时仍暂停。
4. 旧记录不重写 ID/Hash。历史异常的核对与修正独立办理，不借此自动修补所有旧账目。

**验收：** 在事务前后、响应保存后、部分 Effect 完成后分别中断；确认不重复模型请求、不重复结算；无法判断的外部操作保持暂停。该测试只证明列出的路径，不作全系统 Exactly-Once 承诺。

### A4. 统一真实轮次、终态与页面可见进度

**实施：**

- 明确区分 last_completed_round 与 executing_round；失败/用户停止/预算中断的半轮不得算作完整轮次。Run 请求终点与实际终点分开。
- 在一条完整轮次成功收尾后才推进已完成轮次；计数依照真实提交记录。世界状态损坏不能回退成 round=0；持久化失败必须作为错误暴露。
- DB、API、UI 共用一套终态映射：完成、用户停止、Run/Global 预算停止、确定失败、恢复暂停。不能 DB=FAILED、API=STOPPED、页面=READY。
- 复用已有 Run/调用/消息记录提供状态，必要时只增加最少的持久化字段，不建立第二套状态日志。显示当前阶段、最近完成时间、已完成消息/调用数、预算和待处理数量。
- 前端连接失败显示“状态无法确认”，不能继续渲染绿色 READY 为实时状态；短 Run 也必须显示最后一条结束摘要。

**验收：** 世界 25 开始执行 26，26 中途失败时显示“已完成 25 / 中断于 26”；完整结束才推进 26。调用缓慢时能看见等待阶段，不以暂无完成消息误判卡死。重启后摘要与持久化记录一致。

## 3. 方向二：能力声明与真实能力一致，并减少空转

### B1. 工具目录、Prompt 与执行门禁使用同一能力判定

**实施：**

1. 删除基础提示词“仅有三个 Artifact 工具”的过时限制，改为以本 Run 的有效目录为准；保留三输入隔离、单 Step 最多三项、原有权限边界。
2. 区分“已注册”“配置启用”“生产适配器就绪”。有效可用 = 启用且实现/必要配置就绪；配置就绪不能声称网络已连通。
3. Registry 提供同一可用性结果给 Prompt Catalog、UI 目录与 ToolRuntime；不可用工具不作为可调用工具列入模型目录，UI 仍显示工具及简洁原因；伪造调用在执行边界明确拒绝。
4. tools.json 无效时明确阻断配置装配，不回退为全部默认启用。任何能力检查不得向模型返回凭据。
5. 每次 Run 开始锁定基础 Prompt、创世/临时 Prompt 与有效工具目录；保存实际 revision/hash，与生成请求一致。运行中不悄悄变更目录。

**验收：** VPS 无 Client 时，模型目录、UI 和执行结果一致；有配置但没 Client 不显示可调用；禁用、配置错误、适配器就绪分别覆盖。通过实际 server 装配捕获请求，检查不再出现矛盾能力说明。

### B2. 先完成一个真实 VPS 只读闭环，不伪装已恢复全部工具

**实施：**

- 首期明确装配现有 `vps_list_files` 的生产 SSH 适配器，复用受控配置、主机校验、路径和超时边界；不通过关闭主机校验解决连接问题。
- 配置只在工具 Adapter 读取；Runtime 不获得私钥正文，模型不读取连接凭据。
- 其余五项 VPS 能力在真实实现完成前保持不可用并说明原因，不用列表接口替代其实现，不返回 Mock SUCCESS。
- 离线测试通过注入 Client 完成。真实连通性只在授权后验证指定目录列表；本计划不授权远端命令执行、写文件、上传或部署。

**验收：** Client 确实收到目标列表请求并返回真实文件清单；认证失败、路径拒绝、超时均可辨。Mock 仅显式测试使用。五项尚未实施的能力不能因共享 SSH Client 存在就被误标为可执行。

### B3. 先修反馈放大与调度饥饿，再限制重复请求

以下调整涉及实际调度行为，应作为明确整改差异验收，不能声称完全没有行为变化。

**第一步：恢复紧凑反馈与公平队列。**

- 同一 Step 内工具执行结果汇总为一条反馈，保留全部已执行工具的顺序、状态与结果；失败后的剩余工具按既定规则跳过，不伪造回执。
- 普通工具/环境反馈按正常 FIFO 排队；只有明确的控制事件可走已有队首优先入口。不能再用 is_feedback 将所有反馈无限优先。
- 建立稳定入队顺序，在时间戳相同情况下仍确定。消息来源、原始关联 ID、实际产生顺序可核查。
- 真实等待外部输入时允许 STOP；基础行为指引明确“无新证据不重复列目录/读同一文件/给自己派同一任务”，但不强制商业策略和产出。

**第二步：窄范围去重，不丢工作。**

- 同一 Pixel、同一 environment 内容版本已存在未消费请求结果时，不再产生重复的环境消息；首次读取、内容变化或前次已消费后的显式读取保持可用。
- SELF 去重仅针对同一发送/接收者、完全相同内容、相同目标轮次的未消费消息；不同内容、其他 Pixel 消息、已经消费后的请求不得合并。
- 仅合并队列中尚未消费的等价新消息，不删除历史消息，不用大模型语义相似度判断重复，也不把错误反馈悄悄丢掉。
- 去重结果提供观察者计数；不为每次去重再生成一条模型消息，以免制造新的循环。

**验收：** 一次 Step 的三个工具只产生一条完整反馈；持续生成反馈不能饿死已排队邻居消息。相同环境待消费时重复请求只保留一个有效结果，环境改动可送达。不同任务内容和真实用户消息不被误合并。

### B4. 用可解释的停止条件约束空转

**实施：**

- 先执行 B3 并观察隔离回放结果，不增加通用“智能停机”系统。
- 为可重复的纯读取循环增加一个可配置上限：同一 Pixel 连续三次（默认值，须配置化）执行相同的只读工具序列、相同参数并得到相同结果，且输入来源/内容相同、没有新环境/外部/邻居输入、没有写操作/转账/复制/对外路由，判为重复读取循环。
- 仅排除 duration/时间戳等明确观测字段后比较；文件内容变化、读取结果变化或不同新输入重置计数。心智中的轮次自增不单独作为“新事实”。
- 达阈值停止当前 Run，给出专用停止原因及证据摘要（工具名、重复次数、关联消息），保留未消费消息，不增加新的自动重试或自动重启。
- 未达该精确条件的模式先在 UI 暴露重复次数和队列增长，不因“无收入/无交付物”自动停机。只读调查本身可以是有效工作。
- 重启/新 Run 不应被旧计数无依据锁死；是否恢复由已存在的安全门禁与实际新输入决定，不引入新的永久封禁状态。

**验收：** 固定读循环在上限内停止且无新增付费调用；正常读取不同资料、环境变化、邻居新消息不会被误停。声明阈值触发前最多发生多少调用，不能只在 UI 提示后继续无限运行。

## 4. 执行顺序与交付物

1. A1/A2：先建立恢复门禁与未知结果边界，阻止不安全重跑。
2. A3/A4：补齐响应复用、正常结算原子性和一致状态，恢复可验证进度。
3. B1：统一能力声明；B2 的真实 SSH 实现可独立验收，未完成时保持能力不可用。
4. B3：先减少反馈与待消费重复任务；以队列变化和真实调用数验证效果。
5. B4：只对精确定义的重复读取加上限，不扩展为模糊“价值判断”。

每阶段交付修改文件、测试结果、DB/API/UI 对照和未完成项。更新 README 时不得把未实现的 VPS 工具、未通过的恢复场景写成已完成。

## 5. 最小验收矩阵

| 场景 | 必须成立 |
| --- | --- |
| 运行中进程退出，再启动 | 无虚假 RUNNING；未知调用不退款不重发，UI 给出恢复原因 |
| 已收响应后崩溃 | 复用同一调用结果；结算至多一次；未决外部 Effect 不自动重做 |
| 供应商超时/响应体中断/取消 | 按阶段保留 UNKNOWN，不能一律退款 |
| 第 26 轮中途失败 | 已完成轮次不虚增，DB/API/UI 终态与错误一致 |
| 第 26 轮正常完成 | completed round 变为 26，计数与持久化记录一致 |
| VPS 配置存在但没有 Client | UI/模型目录/执行门禁一致地标为不可用 |
| 三工具 Step | 顺序执行、完整汇总、一条反馈，后续业务行为遵循原边界 |
| 反馈不断产生 | 已排队普通消息不被永久饥饿 |
| 环境结果未消费时重复读取 | 不重复入队同版本结果；新版本仍可送达 |
| 完全相同纯读取循环 | 有界停止，无队列清空、无余额修改、无自动续跑 |
| 新资料/环境变化/邻居消息 | 不被去重或循环上限误吞 |
| Mock 验收 | 显式隔离模式，即使本机有真实模型密钥也不意外调用真实供应商 |

最终在 Chrome 检查一条正常 Run、一条确定失败、一条恢复暂停和一条重复读取停止。真实付费/远端验证与离线自动化结果分别报告；不能仅凭单元测试数量宣告运行可信。
